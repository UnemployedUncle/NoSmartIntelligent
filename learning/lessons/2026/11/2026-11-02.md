# No Smart Intelligent | 2026.11.02 (월)
**Today's Topic: Outcome-based Agent Evaluation — 말이 아닌 실제 상태로 성공 검증**

**Today's Key Expression: “Verify the final state, not just the agent's claim.”**

약 10분 학습 · 핵심 표현 1개 + 확장 표현 5개 · 영어 예문 8개

## 1. 오늘의 학술 용어와 근거

### Outcome-based Agent Evaluation — 결과 기반 에이전트 평가 (풀이)

에이전트가 작업을 마쳤다고 **말했는지**가 아니라, 실제 시스템에서 **요구된 최종 상태가 만들어졌는지**를 확인하는 평가 접근입니다. 단일한 보편적 점수 이름이 아니라 에이전트의 업무 완수 여부를 검증하는 설계 방식입니다. 결과 검증과 함께 권한·필수 절차·응답 품질도 별도로 평가할 수 있습니다. [S1][S2]

**관련 용어 두 개:** **Outcome**은 실행 종료 시 환경의 실제 상태이며, **Trace (Trajectory)**는 도구 호출·중간 결과·메시지 등을 포함한 실행 경로입니다. Outcome은 *성공했는가*를, Trace는 주로 *어떻게 진행되었고 왜 실패했는가*를 살펴보는 데 유용합니다. [S1]

**가상 업무 사례 — 청구서 초안 생성 Agent.** 사용자가 청구서 초안을 저장해 달라고 요청했고 Agent가 “저장했습니다”라고 답했다고 가정하겠습니다. 평가기는 메시지만 읽고 성공을 인정하는 대신, 테스트 시스템에 올바른 거래처·필드를 가진 초안 레코드가 남았는지 확인합니다. 하지만 저장된 결과가 맞더라도 승인되지 않은 변경을 시도했다면 별도의 보안·절차 검사에서 실패 처리해야 합니다.

**혼동하기 쉬운 구별:** Trace에 특정 함수 호출이 보인다고 업무가 성공한 것은 아닙니다. 반대로 다른 순서의 허용된 도구 사용으로 동일한 목표 상태에 도달했다면, 순서가 다르다는 이유만으로 반드시 실패 처리할 필요는 없습니다. Anthropic은 지나치게 경직된 경로 검사보다 실제 산출 결과를 평가할 것을 권고하지만, 보안상 반드시 지켜야 하는 행동 제약은 별도로 검증해야 합니다. [S1]

**원문 발췌 [S1]:** “The outcome is the final state in the environment at the end of the trial.”

여기서 **final state**는 Agent의 자기 보고가 아니라 **평가 환경에 실제로 남은 상태**입니다. 이를 고객에게 설명하기 쉽게 바꾼 문장이 오늘의 **“Verify the final state, not just the agent's claim.”**입니다.

**오늘 확인한 공식 자료**

**[S1] Anthropic Engineering — *Demystifying evals for AI agents*** (2026년 1월 9일, 공식 엔지니어링 해설). Task·trial·grader·trace·outcome의 정의와 결과·경로 평가의 차이를 확인했습니다. [원문](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**[S2] OpenAI — *Evaluation best practices*** (공식 평가 설계 가이드, 게시·수정일 미확인; 2026년 11월 2일 열람). 업무별 성공 기준, 평가 사례, 측정 지표, 인간 검토의 필요성을 교차 확인했습니다. 문서의 특정 Evals 플랫폼은 종료 절차 중이므로 여기서는 플랫폼 기능이 아니라 일반 평가 원칙만 다룹니다. [원문](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 2. 고객에게 설명하는 영어

아래 예문은 확인한 공식 자료를 바탕으로 새로 작성한 **설명용 재작성 및 가상 업무 설계**입니다. 실제 고객사의 성능을 주장하지 않습니다.

### ⭐ ① Verify the final state, not just the agent's claim

> Outcome-based agent evaluation checks whether the required final state was reached, not just whether the agent claimed success.

**해석:** 결과 기반 에이전트 평가는 에이전트가 성공했다고 말했는지가 아니라 필요한 최종 상태가 실제로 달성되었는지를 확인합니다.

**활용:** 평가의 목적을 정의할 때. 최종 답변과 실제 업무 결과를 구분합니다. [S1][S2]

### ② Define observable success criteria before a trial

> For the proposed invoice assistant, we would define success as a correctly saved draft with the expected supplier and fields.

**해석:** 제안하는 청구서 보조 시스템에서는 예상한 공급업체와 필드가 맞는 초안이 실제 저장된 상태를 성공으로 정의하겠습니다.

**활용:** 테스트 시작 전에 합격 기준을 구체화할 때. [S1][S2]

### ③ Check the system record against the requested action

> After a simulated invoice update, the grader checks the stored record against the requested status and values.

**해석:** 모의 청구서 갱신 후 평가기는 저장된 기록의 상태와 값이 요청 내용에 부합하는지 확인합니다.

**활용:** 실제 시스템 상태를 검증하는 평가기를 설명할 때. [S1]

### ④ Inspect the trace to diagnose a failed outcome

> If the expected draft is missing, we inspect the trace to locate a failed tool call or an incorrect argument.

**해석:** 예상한 초안이 없다면 도구 호출 실패나 잘못된 인자를 찾기 위해 실행 기록을 점검합니다.

**활용:** 실패 원인을 분석할 때 결과와 실행 이력을 연결합니다. [S1]

### ⑤ Allow different valid paths to the same outcome

> We should allow different valid tool sequences to pass when they produce the required result without violating constraints.

**해석:** 제약 조건을 어기지 않고 필요한 결과를 만든다면 도구 사용 순서가 달라도 통과하도록 해야 합니다.

**활용:** 특정 도구 순서를 과도하게 강제하는 평가의 문제를 설명할 때. [S1]

### ⑥ Combine outcome checks with process safeguards

> In the proposed workflow, we would verify the saved invoice and check that no unauthorized action was attempted.

**해석:** 제안하는 워크플로에서는 청구서 저장 여부를 검증하고 승인되지 않은 행동을 시도하지 않았는지도 확인하겠습니다.

**활용:** 최종 결과와 필수 보안·승인 제약을 동시에 평가할 때. [S1][S2]

**같은 개념을 청중에 따라 설명하기**

**For Business Executives**

> An agent saying an invoice was created is not proof; we would confirm the record in the system before counting the task as complete.

**해석:** 에이전트가 청구서를 만들었다고 말하는 것만으로는 충분하지 않습니다. 실제 시스템 기록을 확인한 뒤 업무 완료로 판정하겠습니다. [S1]

**For Technical Teams**

> We would grade the persisted end state, monitor permission constraints, and inspect traces only when we need to explain failures.

**해석:** 저장된 최종 상태를 평가하고 권한 제약을 감시하며, 실패 원인을 분석할 필요가 있을 때 실행 기록을 조사하겠습니다. [S1][S2]

## 3. 오늘의 한 문제

### Consultant's Challenge — Shipment-booking Agent

**가상 업무 상황:** 물류 회사가 선적 예약 Agent를 시험합니다. Agent는 “예약이 완료되었습니다”라고 답했지만 실제 운영 시스템에 예약 번호가 남았는지는 아직 확인하지 않았습니다. 고객은 성공 여부를 어떻게 검증하고, Agent가 항상 같은 도구 호출 순서를 따라야 하는지 묻습니다.

**Customer Question**

> **“Our shipment-booking agent says the booking is complete. How would you prove it actually succeeded, and should every successful run use exactly the same tool sequence?”**

영어 **3~5문장, 약 40~70단어 또는 30~45초**로 답해 보세요. **필수 표현:** “Verify the final state, not just the agent's claim.” **선택 표현(하나만):** “Check the system record against the requested action” 또는 “Allow different valid paths to the same outcome”. 실제 예약 레코드가 확인되어야 성공을 인정할 수 있다는 점을 설명하고, 허용된 대체 경로와 지켜야 할 제약을 구분하세요. 검증되지 않은 실제 운영 성능은 단정하지 마세요.
