# No Smart Intelligent | 2026.11.19 (목) — Prefill/Decode Disaggregation

**Today's Key Expression: “Separate prompt processing from token generation to optimize each phase independently.”**

약 10분 학습 · 핵심 1개 + 확장 5개 · 청중별 예문 2개

## 1. 오늘의 학술 용어와 근거

**Prefill/Decode Disaggregation (PD Disaggregation) — 프리필·디코드 분리 서빙(풀이)**

LLM 추론의 **prefill**은 입력 프롬프트를 처리하여 다음 토큰 생성을 위한 내부 상태를 계산하는 단계이며, **decode**는 그 상태를 활용해 출력 토큰을 순차적으로 생성하는 단계입니다. **Prefill/decode disaggregation**은 두 단계를 서로 다른 GPU/TPU 워커 또는 노드에 배치하여 각 단계의 자원을 독립적으로 조정하는 *추론 서빙 아키텍처*입니다. 일반적으로 프리필은 계산량의 영향을 크게 받고 디코드는 메모리 대역폭의 영향을 받지만, 이 구조가 모든 요청에서 성능 향상을 보장하지는 않습니다. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**관련 용어 두 개**

- **Time to First Token (TTFT) — 첫 토큰까지 걸리는 시간:** 요청을 보낸 뒤 첫 출력 토큰을 받을 때까지의 지연입니다.
- **Time per Output Token (TPOT) — 출력 토큰당 시간:** 이후 토큰들이 출력되는 속도를 평가하는 지표입니다. 측정 방식에 따라 첫 토큰은 제외합니다.

**가상 업무 예시 — 장문 보고서 요약:** 가상의 유통사가 100페이지 보고서에서 핵심 내용만 요약하도록 한다고 가정하겠습니다. 긴 입력과 짧은 출력 때문에 프리필 워커가 혼잡할 가능성을 먼저 점검하고, 별도 디코드 워커를 배치해 자원을 달리 할당하는 방식을 실험할 수 있습니다. 하지만 두 워커 사이에 **KV 캐시를 이동하는 시간**과 대기열, 동시 요청 수준에 따라 오히려 지연이 늘 수도 있습니다. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**오늘의 구별 — 단계 분리 ≠ 단순히 모델을 두 개 실행:** 서로 독립된 두 언어 모델이 각각 답을 만드는 것이 아닙니다. 통상 동일 모델의 서로 다른 추론 단계를 별도 워커가 맡고 프리필에서 만든 KV 캐시 상태를 디코드 워커로 전달합니다. 반면 통합형(colocated) 서빙은 같은 자원에서 두 단계를 수행합니다. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/)

**원문 요지 [S1] → 설명용 재작성:** NVIDIA는 두 단계가 서로 다른 연산 자원에 민감하며, 분리하면 각각을 별도로 최적화할 수 있지만 KV 캐시 전송 및 대기 시간이 설계 선택에 영향을 준다고 설명합니다. 이를 고객에게 간결하게 설명하면 **“Separate prompt processing from token generation to optimize each phase independently.”**입니다. 이 문장은 원문 인용이 아니라 기술적 의미를 재구성한 표현입니다.

**확인한 자료**

- **[S2] Google Cloud**, Reena Singhal Lee, *From LLMs to image generation: Accelerate inference workloads with AI Hypercomputer*, **2025-05-09**, [공식 원문](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu). 역할: JetStream/Pathways의 독립 확장과 TTFT·TPOT 측정의 실제 구현·실험 맥락을 교차 확인한 기술 글(동료심사 논문 아님).

## 2. 고객에게 설명하는 영어

**1. 핵심 — Separate prompt processing from token generation to optimize each phase independently**

> Disaggregated serving places the prefill stage and the decode stage on separate workers so that each phase can be scaled independently.

**해석:** 분리형 서빙은 프리필 단계와 디코드 단계를 서로 다른 워커에 배치해 각 단계를 독립적으로 확장할 수 있게 합니다. **활용:** 기법의 정의와 목적을 처음 설명할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**2. 확장 — Treat prefill as compute-intensive and decoding as memory-bandwidth-sensitive**

> Prefill typically processes prompt tokens with substantial parallel computation, whereas decoding repeatedly generates new tokens and is often limited by memory bandwidth.

**해석:** 프리필은 보통 프롬프트 토큰을 병렬 계산으로 처리하는 반면, 디코딩은 새 토큰을 반복 생성하고 메모리 대역폭의 제약을 자주 받습니다. **활용:** 두 단계의 리소스 특성이 다른 이유를 설명할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/)

**3. 확장 — Transfer the KV cache between prefill and decode workers**

> After prefill, the serving system must transfer the relevant KV cache to the decode workers before they continue generating output tokens.

**해석:** 프리필 이후 서빙 시스템은 디코드 워커가 출력 토큰 생성을 이어가기 전에 필요한 KV 캐시를 전달해야 합니다. **활용:** 분리 시 추가되는 데이터 이동과 지연 요인을 설명할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/)

**4. 확장 — Allocate capacity according to input and output lengths**

> For long reports with short summaries, we would test whether allocating more prefill capacity removes the main bottleneck.

**해석:** 긴 보고서를 짧게 요약하는 업무에서는 프리필 용량을 더 배정할 때 주된 병목이 해소되는지 시험하겠습니다. **활용:** 입력·출력 길이에 맞춰 자원을 배분하는 설계 옵션을 설명할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**5. 확장 — Track time to first token separately from time per output token**

> We would measure time to first token and time per output token separately because a faster first response does not guarantee faster subsequent token generation.

**해석:** 첫 토큰 지연과 출력 토큰당 시간을 따로 측정하겠습니다. 처음 응답이 빨라도 이후 토큰 생성까지 빠르다는 뜻은 아니기 때문입니다. **활용:** 사용자가 체감하는 두 종류의 지연을 구별할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**6. 확장 — Benchmark disaggregated serving against a colocated baseline**

> We would compare disaggregated and colocated serving with the same model, hardware budget, input and output lengths, and request concurrency.

**해석:** 동일한 모델, 하드웨어 예산, 입출력 길이, 동시 요청 수준에서 분리형과 통합형 서빙을 비교하겠습니다. **활용:** 실제 속도와 비용 개선을 확인할 비교 실험을 제안할 때. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**청중별 변형 — 임원/비전공 현업**

> Separating prompt processing from answer generation could improve service capacity, but we would verify latency and cost on your actual request mix before committing.

**해석:** 프롬프트 처리와 답변 생성을 분리하면 서비스 수용량이 개선될 수 있지만, 도입 전 실제 요청 구성에서 지연과 비용을 검증하겠습니다. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

**청중별 변형 — 기술팀**

> We would profile prefill and decode utilization, KV-cache transfer overhead, first-token latency, and output-token latency under matched GPU budgets.

**해석:** 동일한 GPU 예산에서 프리필·디코드 사용률, KV 캐시 전송 오버헤드, 첫 토큰 지연, 출력 토큰 지연을 측정하겠습니다. [S1](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) [S2](https://cloud.google.com/blog/products/compute/ai-hypercomputer-inference-updates-for-google-cloud-tpu-and-gpu)

## 3. 오늘의 한 문제

**Consultant's Challenge — Customer Support with Long Policies**

**가상 상황:** 가상의 고객센터 AI는 매우 긴 정책 문서를 읽고 짧은 고객 질문에 답합니다. 공급업체는 프리필과 디코드를 분리하면 모든 상황에서 지연이 감소한다고 주장하지만, 실제 트래픽의 입력·출력 길이와 동시 요청 부하는 아직 측정하지 않았습니다.

**Customer Question**

> Our support assistant answers short customer questions using very long policy documents. A vendor says separating prefill and decode will always cut latency. Would you deploy that architecture without testing our traffic first?

영어 **3~5문장, 약 40~70단어** 또는 **30~45초**로 답하세요. 예문을 그대로 복사하지 말고 업무 상황에 맞게 변형해 보세요.

**필수 표현:** “Separate prompt processing from token generation to optimize each phase independently.”

**선택 표현 (하나만):** “Transfer the KV cache between prefill and decode workers” 또는 “Benchmark disaggregated serving against a colocated baseline”.

**작성 과제:** 프리필과 디코드를 분리하는 작동 원리를 설명하고, KV 캐시 이동 또는 동일 조건의 비교 실험을 하나 포함하세요. 검증하지 않은 지연 개선이나 비용 절감을 약속하지 마세요.
