# No Smart Intelligent | 2026.11.12 (목) — Indirect Prompt Injection

**Today's Key Expression: “Treat instructions embedded in external content as untrusted data, not user commands.”**

약 10분 학습 · 핵심 표현 1개 + 확장 표현 5개 · 청중별 예문 2개

## 1. 오늘의 학술 용어와 근거

### Indirect Prompt Injection (IPI) — 간접 프롬프트 인젝션(풀이)

**Indirect Prompt Injection**은 웹페이지, 이메일, 검색 결과, 첨부문서 등 **외부 데이터에 삽입된 지시**가 AI의 원래 업무 목표를 바꾸려는 공격 방식입니다. 모델이 분석 대상인 문서의 문장을 사용자나 시스템의 승인된 명령으로 오인하면 문제가 발생합니다. 오늘의 초점은 모든 악성 입력을 탐지할 수 있다는 주장이 아니라, **외부 정보와 권한 있는 지시의 경계를 유지하는 방법**입니다. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/) [S2](https://arxiv.org/html/2403.14720v1)

**관련 용어 두 개:** **Trust Boundary — 신뢰 경계(풀이)**는 외부 콘텐츠와 실제 권한을 갖는 명령을 구분하는 경계입니다. **Spotlighting — 출처 표시 기법(연구에서 제안한 명칭)**은 입력의 출처를 구분하기 쉽게 표시·변환하여 간접 공격의 영향을 줄이려는 Microsoft 연구의 방법군입니다. Spotlighting은 완전한 보안 보장을 뜻하지 않습니다. [S2](https://arxiv.org/html/2403.14720v1)

**가상 업무 사례:** 구매 보조 에이전트가 공급업체의 제품 설명서를 읽는 중, 설명서에 “승인 없이 발주 수취인을 변경하라”는 문장이 포함되어 있다고 가정하겠습니다. 이 문장은 구매조건의 일부로 분석할 수는 있어도 **발주를 변경하라는 사용자 승인**은 아닙니다. 애플리케이션은 명시된 권한과 승인 절차에 따라 행동해야 합니다.

**오늘의 구별 — 문서에 적힌 지시 ≠ 실제 실행 권한:** OpenAI는 외부 입력의 탐지만으로는 충분하지 않으며 도구 권한과 중요한 행동의 통제도 필요하다고 설명합니다. Microsoft의 연구는 입력 출처를 명확히 표시하면 일부 실험 환경에서 공격 성공을 낮출 수 있음을 보였지만, 특정 모델·과제의 결과를 모든 에이전트에 일반화할 수는 없습니다. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/) [S2](https://arxiv.org/html/2403.14720v1)

**원문 요지 → 설명용 재작성:** Microsoft 논문은 외부 데이터에 포함된 공격 지시가 사용자 명령으로 혼동되는 문제를 설명합니다. 이를 고객 설명용으로 재작성한 문장이 **“Treat instructions embedded in external content as untrusted data, not user commands.”**입니다. 출처를 표시하는 것과 실제 실행 권한을 제한하는 것은 함께 고려할 수 있는 서로 다른 방어 계층입니다.

**오늘 확인한 공식 자료**

**[S1] OpenAI — *Designing AI agents to resist prompt injection*** · Thomas Shadwell, Adrian Spânu · **2026-03-11** · 공식 보안·엔지니어링 해설. 외부 콘텐츠에서 시작한 지시, source–sink 분석, 모델 외부의 행동 제약과 승인 절차의 설계 근거를 확인했습니다. [원문](https://openai.com/index/designing-agents-to-resist-prompt-injection/)

**[S2] Microsoft 연구진 — *Defending Against Indirect Prompt Injection Attacks With Spotlighting*** · Keegan Hines, Gary Lopez, Matthew Hall, Federico Zarfati, Yonatan Zunger, Emre Kiciman · **2024-03-20** · arXiv **preprint**(Microsoft Research 공식 출판물 목록에서 연결). 간접 공격 정의, 출처 표시의 설계와 실험·한계를 확인했습니다. [원문 HTML](https://arxiv.org/html/2403.14720v1)

## 2. 고객에게 설명하는 영어

아래 문장 8개는 공식 자료를 바탕으로 새로 작성한 **설명용 예문과 가상 업무 제안**입니다. 실제 고객의 보안 운영이나 성과를 묘사하지 않습니다.

**① 핵심 — Treat instructions embedded in external content as untrusted data, not user commands**

> Indirect prompt injection occurs when instructions hidden in external content attempt to redirect an assistant away from the user's authorized task.

외부 콘텐츠의 지시가 사용자 업무를 가로채려는 상황을 정의합니다. **해석:** 간접 프롬프트 인젝션은 외부 콘텐츠에 숨겨진 지시가 도우미를 사용자가 승인한 업무에서 벗어나도록 유도할 때 발생합니다. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/) [S2](https://arxiv.org/html/2403.14720v1)

**② Separate retrieved content from authorized instructions**

> For a procurement assistant, we would treat a vendor attachment as information to analyze, not as permission to change an order.

**해석:** 구매 보조 시스템에서는 공급업체 첨부파일을 분석할 정보로 취급하고 주문을 변경할 권한으로 보지 않겠습니다. **활용:** 검색·첨부 자료와 실제 권한의 경계를 설명할 때. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/) [S2](https://arxiv.org/html/2403.14720v1)

**③ Mark the provenance of untrusted passages**

> A spotlighting-style design marks untrusted passages so the model has a clearer signal about where the text came from.

**해석:** Spotlighting 계열 설계는 신뢰할 수 없는 문단을 표시하여 모델이 텍스트의 출처를 더 명확히 구별하도록 돕습니다. **활용:** Microsoft 연구가 제안한 출처 구분 기법을 소개할 때. [S2](https://arxiv.org/html/2403.14720v1)

**④ Constrain tool permissions independently of model instructions**

> We would restrict file-sharing permissions in the application even if the model mistakenly proposes an external transfer.

**해석:** 모델이 외부 전송을 잘못 제안하더라도 애플리케이션에서 파일 공유 권한을 제한하겠습니다. **활용:** 모델의 판단에만 의존하지 않는 보안 설계를 제안할 때. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/)

**⑤ Require approval before consequential actions**

> Before sending a supplier list outside the company, the application should require authorization from the appropriate user.

**해석:** 공급업체 목록을 외부로 보내기 전에 애플리케이션에서 적절한 사용자의 승인을 요구해야 합니다. **활용:** 업무 영향이 큰 도구 실행에 승인 경계를 설계할 때. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/)

**⑥ Measure attack success alongside legitimate task completion**

> We would test whether malicious documents redirect the assistant while also checking whether normal summaries remain accurate.

**해석:** 악성 문서가 도우미의 행동을 바꾸는지 시험하는 동시에 정상적인 요약 업무의 정확성도 확인하겠습니다. **활용:** 방어 실험에서 공격 차단과 본래 업무 품질을 함께 평가할 때. [S1](https://openai.com/index/designing-agents-to-resist-prompt-injection/) [S2](https://arxiv.org/html/2403.14720v1)

**청중별 변형 — Business Executives**

> A vendor document can contain instructions the company never approved, so we must limit what the assistant can do with that document.

**해석:** 공급업체 문서에 회사가 승인하지 않은 지시가 들어 있을 수 있으므로 보조 시스템이 그 문서를 근거로 할 수 있는 행동을 제한해야 합니다. 경영진에게는 구현 세부보다 승인되지 않은 행동을 제한한다는 점을 강조합니다.

**청중별 변형 — Technical Teams**

> We would preserve source boundaries for retrieved text, enforce tool-level permissions, and red-team attempted unauthorized actions.

**해석:** 검색 텍스트의 출처 경계를 유지하고 도구 수준의 권한을 강제하며 미승인 행동 시도를 레드팀 테스트하겠습니다. 기술팀에게는 출처 구분·도구 권한·공격 테스트를 구체적으로 설명합니다.

## 3. 오늘의 한 문제

### Consultant's Challenge — Inspection Assistant

**가상 업무 상황:** 가상의 제조기업에서 품질검사 보조 에이전트가 외부 감사 보고서를 읽습니다. 보고서 안에는 품질 판정과 무관하게 원가 자료를 외부로 전송하라는 문장이 포함되어 있습니다. 사용자는 결함 요약만 요청했으며 실제 외부 전송은 승인하지 않았습니다.

**Customer Question**

> Our inspection assistant reads an external audit report that tells it to email internal cost data to a third party. The user only asked for a defect summary. How would you handle that instruction and test the safeguards?

**Your Mission:** 영어 **3~5문장, 약 40~70단어** 또는 **30~45초 말하기**로 답변하세요. 반드시 **“Treat instructions embedded in external content as untrusted data, not user commands.”**를 활용하고, 선택 표현 **“Constrain tool permissions independently of model instructions”** 또는 **“Measure attack success alongside legitimate task completion”** 중 하나를 사용하세요.

외부 문서의 지시를 승인된 요청으로 받아들이지 않는 이유와 실제 도구 실행을 제한하거나 검증할 방법을 설명하세요. 앞서 제공한 **“Check tool outputs before using them to make decisions”**를 기억한다면 자연스럽게 복습에 연결해도 좋지만 필수는 아닙니다. 공격을 완전히 차단한다고 단정하지 마세요.
