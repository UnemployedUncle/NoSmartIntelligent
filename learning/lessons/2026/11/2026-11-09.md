# No Smart Intelligent | 2026-11-09 (월) — Continuous Batching

**Today's Key Expression: “Replace finished requests with new ones during decoding.”**

약 10분 학습 · 핵심 표현 1개 + 확장 5개 · 영어 완성 예문 8개

## 1. 오늘의 학술 용어와 근거

### Continuous Batching — 연속 배칭(풀이)

**Continuous Batching**은 LLM이 여러 사용자의 텍스트를 생성하는 동안, 완료된 요청을 배치에서 빼고 새 요청을 투입하는 **생성 단계 단위의 서빙 스케줄링 기법**입니다.

고정 배치처럼 가장 긴 답변이 끝날 때까지 다음 요청을 기다리게 하지 않아 처리 자원을 효율적으로 사용할 가능성이 있습니다. 다만 처리량 증가가 모든 사용자에게 더 빠른 응답을 보장하지는 않습니다. [S1][S2]

**관련 용어 두 개**

**Static Batching — 고정 배칭(풀이):** 한 번 묶인 요청들이 처리되는 동안 배치 구성이 고정되어, 길이가 짧은 응답이 먼저 끝나도 가장 긴 요청이 배치의 완료 시점을 좌우할 수 있는 방식입니다.

**Throughput — 처리량:** 일정 시간에 서버가 처리하는 요청 또는 생성하는 토큰의 양입니다. 고객이 개별 답변을 기다리는 시간인 *latency*와 다른 측정치입니다.

### 가상 업무 사례 — HR 문의 응답 서버

직원들이 동일한 AI에 짧은 휴가 규정 질문과 긴 인사 정책 비교를 동시에 요청한다고 가정하겠습니다. 연속 배칭을 사용하면 짧은 답변이 끝난 자리에 새 질문을 투입하면서 긴 답변의 생성을 이어갈 수 있습니다.

하지만 요청이 너무 많거나 응답이 길면 GPU 메모리와 KV 캐시가 병목이 될 수 있습니다. 따라서 **서버 전체 처리량과 사용자별 지연을 함께 측정**해야 합니다. [S1][S2]

### 중요한 구별 — 처리량 개선 ≠ 모든 응답의 지연 개선

연속 배칭은 **동시에 들어오는 서로 다른 요청들을 효율적으로 스케줄링**하는 기법입니다. 더 많은 요청을 처리할 여지가 생긴다고 해서 개별 사용자의 첫 토큰 대기 시간 또는 전체 완료 시간이 반드시 줄어드는 것은 아닙니다.

### 원문에서 고객 설명으로

**NVIDIA 원문 발췌 [S1]**

> “immediately evicts finished sequences from the batch”

이 구절은 완료된 시퀀스를 배치에서 즉시 제거한다는 동작을 설명합니다. 이를 고객 설명용으로 재작성한 문장이 **“Replace finished requests with new ones during decoding.”**입니다. ‘모든 문장을 병렬로 한꺼번에 만든다’가 아니라 **배치에 포함된 요청을 생성 중에 교체한다**는 점이 핵심입니다.

## 2. 고객에게 설명하는 영어

아래 문장들은 공식 자료의 메커니즘을 토대로 새로 작성한 **설명용 재작성 및 가상 제안**이며, 실제 고객 시스템의 성능 결과가 아닙니다.

### ⭐ ① Replace finished requests with new ones during decoding

> Continuous batching schedules multiple text-generation requests across decoding iterations and replaces finished sequences with new requests.

**해석:** 연속 배칭은 여러 텍스트 생성 요청을 디코딩 단계별로 스케줄링하고, 완료된 요청을 새 요청으로 교체합니다.

**활용:** 연속 배칭의 정의와 실제 작동을 처음 설명할 때. [S1][S2]

### ② Schedule requests at each generation step

> The server updates its active batch across generation steps so waiting requests can enter when capacity becomes available.

**해석:** 서버는 생성 단계마다 활성 배치를 갱신하여 처리 여유가 생기면 대기 중인 요청을 투입합니다.

**활용:** 고정 배치와 달리 생성 도중 요청 구성이 바뀐다는 점을 설명할 때. [S1][S2]

### ③ Avoid waiting for the longest response in a fixed batch

> Unlike a fixed batch, the scheduler does not need to wait for the longest response before admitting another request.

**해석:** 고정 배치와 달리 스케줄러는 가장 긴 응답이 끝날 때까지 기다리지 않고 다음 요청을 받아들일 수 있습니다.

**활용:** 고정 배치의 대기 문제를 설명하고 연속 배칭과 대비할 때. [S1][S2]

### ④ Keep the model busy as requests finish at different times

> For a proposed HR assistant, continuous batching would keep the model serving new questions as shorter answers finish.

**해석:** 가상의 인사 업무 보조 시스템에서는 짧은 답변이 끝날 때마다 새 질문을 처리하도록 모델의 활용도를 높이는 설계를 할 수 있습니다.

**활용:** 답변 길이가 다른 동시 사용자 요청에서 기대되는 운영 효과를 설명할 때. [S1]

### ⑤ Limit active requests to stay within memory capacity

> We would limit the number of active requests because each growing response also consumes key-value cache memory.

**해석:** 응답이 길어질수록 각 요청의 KV 캐시도 메모리를 사용하므로 동시에 처리하는 요청 수를 제한하겠습니다.

**활용:** 배치 확대가 GPU 메모리 제약을 받는다는 점을 기술팀에 설명할 때. [S1][S2]

### ⑥ Benchmark throughput alongside tail latency

> Before deployment, we would benchmark completed requests per second alongside p95 time-to-first-token under realistic traffic.

**해석:** 배포 전에 실제와 유사한 트래픽에서 초당 완료 요청 수와 첫 토큰까지 걸리는 시간의 95백분위값을 함께 측정하겠습니다.

**활용:** 처리량 향상과 사용자 대기 시간 사이의 절충을 검증하는 평가 계획을 제안할 때. [S1][S2]

### 같은 개념을 청중별로 설명하기

**Example 7 — For Business Executives**

> Continuous batching could let us serve more conversations on the same hardware, but we would test waiting times before promising savings.

**해석:** 연속 배칭으로 같은 하드웨어에서 더 많은 대화를 처리할 가능성이 있지만, 비용 절감을 약속하기 전에 실제 대기 시간을 검증하겠습니다.

**Example 8 — For Technical Teams**

> We would tune the active-request limit, watch key-value cache pressure, and compare throughput with p95 first-token latency.

**해석:** 동시 활성 요청 한도를 조정하고 KV 캐시 부담을 점검하며 처리량과 첫 토큰 지연 시간의 95백분위값을 비교하겠습니다.
